# 技术栈选型

## 1. 核心决策 (Key Decisions)

本项目采用 **Python 3.10+** 作为核心语言，选择理由如下：
*   **与现有系统兼容**：直播系统同样使用 Python 构建，便于无缝集成
*   **丰富的网络库生态**：拥有成熟的代理服务器（mitmproxy）、浏览器自动化（playwright）和协议解析工具
*   **开发效率高**：相比 C#（DouyinBarrageGrab），Python 的开发周期更短，维护成本更低
*   **异步支持完善**：asyncio 原生支持高并发场景，满足 10 个直播间同时监听的需求

## 2. 核心组件选型

### 2.1 代理监听引擎 (Proxy Engine)

| 组件 | 技术选型 | 版本要求 | 选择理由 |
|------|---------|---------|---------|
| **代理服务器框架** | `mitmproxy` | >= 10.0 | ✅ Python 生态最成熟的代理框架<br>✅ 支持 HTTP/HTTPS/WebSocket 全协议<br>✅ 提供异步 API，性能优异<br>✅ 可扩展性强，支持插件机制 |
| **SSL 证书管理** | `certgen` | >= 1.0 | ✅ 自动生成自签名证书<br>✅ 支持 Windows 证书存储信任<br>✅ 与 mitmproxy 深度集成 |
| **进程过滤** | `psutil` | >= 5.9 | ✅ 跨平台进程信息获取<br>✅ 轻量级依赖<br>✅ 实时监控进程状态 |
| **域名白名单** | 内置正则匹配 | - | ✅ 无需额外依赖<br>✅ 性能开销最小<br>✅ 灵活可控 |

**备选方案对比**：
| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **mitmproxy** | Python 原生、生态丰富、文档完善 | 内存占用略高（~80MB） | ✅ **推荐** |
| **pyproxy** | 轻量级、内存占用低 | 功能单一、社区活跃度低 | ❌ 不推荐 |
| **Titanium.Web.Proxy (C#)** | 性能最优、内存占用最低 | 需跨语言调用、维护成本高 | ❌ 不推荐 |

---

### 2.2 Playwright 浏览器引擎 (Browser Engine)

| 组件 | 技术选型 | 版本要求 | 选择理由 |
|------|---------|---------|---------|
| **浏览器自动化框架** | `playwright` (Python) | >= 1.40 | ✅ 微软官方维护，质量有保障<br>✅ 支持 Chromium/Firefox/WebKit 多引擎<br>✅ BrowserContext 隔离机制完善<br>✅ Cookie 持久化 API 成熟 |
| **浏览器内核** | `Chromium` | - | ✅ 市场占有率最高<br>✅ 兼容性最好<br>✅ 内存优化最佳 |
| **Cookie 管理** | Playwright 内置 | - | ✅ `storage_state` 参数一键保存/加载<br>✅ 支持 localStorage/sessionStorage<br>✅ 无需手动操作 Cookie 文件 |
| **脚本执行** | `Jint` (通过 Pyodide) | - | ✅ 纯 JavaScript 引擎<br>✅ 支持 ES6+ 语法<br>✅ 可在 Python 中安全执行 |

**备选方案对比**：
| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **Playwright** | API 现代化、文档优秀、社区活跃 | 首次安装需下载浏览器（~300MB） | ✅ **推荐** |
| **Selenium** | 历史悠久、资料丰富 | API 设计老旧、性能较差 | ❌ 不推荐 |
| **Pyppeteer** | 纯 Python 实现 | 已停止维护、Bug 较多 | ❌ 不推荐 |

### 2.3 统一消息总线 (Unified Message Bus)

| 组件 | 技术选型 | 版本要求 | 选择理由 |
|------|---------|---------|---------|
| **异步运行时** | `asyncio` | Python 3.10+ 内置 | ✅ 标准库，无需额外依赖<br>✅ 性能优异<br>✅ 生态完善 |
| **事件分发** | 自定义 EventBus | - | ✅ 轻量级实现<br>✅ 完全可控<br>✅ 无第三方依赖开销 |

## 6. 技术风险评估

| 风险项 | 影响等级 | 应对措施 |
|--------|---------|---------|
| **mitmproxy 内存占用较高** | 🟡 中等 | 1. 优化域名白名单，减少解密范围<br>2. 定期清理无效连接<br>3. 监控内存使用，必要时重启代理 |
| **Playwright 浏览器崩溃** | 🟢 低 | 1. BrowserContext 隔离防止污染<br>2. 心跳保活机制检测异常<br>3. 自动重启恢复服务 |
| **抖音协议更新导致解析失败** | 🟡 中等 | 1. 预留 .proto 文件版本管理<br>2. 添加协议版本检测逻辑<br>3. 建立降级方案（如切换到轮询模式） |
| **Windows 系统代理冲突** | 🟡 中等 | 1. 启动前检查端口占用<br>2. 提供关闭代理的快捷方式<br>3. 详细的错误提示和修复指南 |

## 8. 总结

本技术选型方案遵循以下原则：
1. **优先选择成熟稳定的开源库**：避免使用实验性项目，降低维护风险
2. **保持依赖精简**：仅引入必要的第三方库，减少潜在冲突
3. **充分利用 Python 标准库**：如 `asyncio`, `gzip`, `collections` 等，降低学习成本
4. **兼顾性能与可维护性**：在保证性能的前提下，优先考虑代码可读性和扩展性
