# ADR-002: 弹幕发送能力约束修订（AutoDanmu）

状态: ACCEPTED | 日期: 2026-10-06 | 关联: /autoplan 全管线评审（44 项裁定 R1-R44，计划文件 ~/.gstack/projects/DanmakuListener/plans/2026-10-06-danmaku-send-plan.md）| 修订: ADR-001 无涉（引擎拓扑不变）

## 背景

设计文档 v1（docs/designs/six-platform-danmaku-rebuild.md:42）约束「只监听、不发送弹幕/礼物」——
v1 时代的范围护栏：最小化风控暴露、聚焦监听稳定性。2026-10-05 十二平台监听全量收官
（v0.5.0）后，AUTOlive 数字人「能听不能说」：评论问答、欢迎互动、弹幕游戏等上层互动
全部以发送能力为前提。BytePlus 官方数字人产品的「评论区文字自动回复」亦标记为尚未
支持（docs.byteplus.com，2026-09 查证）——该能力是已验证存在但未被满足的需求位。

创始人于 2026-10-06 显式裁定突破该约束：开发自动发送弹幕功能，使用已登录账号发送。
本 ADR 记录约束修订的边界、接受的风险与被否决的替代方案，**是发送功能实现的前置条件**
（计划义务块 R1：必须落 ADR 后方可开始实现）。

## 决策

1. **约束修订（R1）**：「只监听、不发送弹幕/礼物」修订为「**允许弹幕发送；礼物发送
   仍然禁止**」。礼物涉及资金与更高风控等级，禁止不在本次修订范围内。
2. **发声主场景（R16）**：发送目标**仅限客户自运营/受托运营的直播间**（即当前监听中
   的房间）——欢迎、答疑、互动均为自家直播间运营增强，不向任意第三方直播间发声。
   技术落点：发送目标限定当前监听中的房间，未监听房间回执拒绝。
3. **账号连坐风险显式接受并申报（R15）**：发送与监听共用账号，发送触发的平台风控
   （禁言/封号）会直接摧毁该平台已交付的监听能力。缓解与预案：
   - 风控防护六件套为验收必需：按平台开关默认全关 / 限速+随机抖动 / 发送前过滤
     （blocked_keywords+长度+去重）/ dry-run 默认开（含抽检出口标准 R20）/ 审计日志
     （fail-closed）/ 失败熔断（恢复=人工重开）。
   - 封禁/禁言检测复用 NEEDS_LOGIN / ROUTE_FAILED 语义扩展「发送触发封禁」识别路径。
   - **监听/发送分账号隔离列为评估项**（故障隔离问题，与已否决的多账号轮换伪装是
     两个问题）；连坐发生时的降级叙事沿用监听侧协议边界申报惯例。
4. **实现边界**：发送架构按 /autoplan 批准计划执行——senders/ 独立子包与监听引擎解耦
   （监听引擎只读语义不动，send 钩子为唯一新增出口且异常隔离）；受控页面 sender 经由
   监听引擎实例执行（persistent context 单实例独占，禁止另开同 profile context）；
   ws/REST 双入口收敛单一命令管线；token 未配置=拒绝启动。细节以批准计划为准。

## 后果

- AUTOlive 数字人获得直播间发声能力（互动闭环的最后一块）；验证期默认 dry-run，
  出口标准=连续 N 次内容抽检合格→实发（切换归属=AUTOlive 配置）。
- 账号级风险敞口从零变为真实存在：任何发送实现缺陷或内容事故都可能导致监听账号被
  限权——审计日志（权威对账）与熔断（自动停用）是止血手段，不是风险消除。
- 2026 合规环境（AI 直播标注等新规）下，自动化公开发言是行业第一风控关切：
  六件套+分平台灰度（M1a→M1b→M2/M3）是该关切的工程回应；平台规则变化可能随时
  收紧甚至关闭个别平台的发送路线（协议边界申报惯例适用）。
- 发送成功的弹幕会回到本系统监听流（自发声回环）：AUTOlive 须按
  DANMU_SEND_RESULT 的 sent_at+content 在对账窗口去重自己的发声。

## 替代方案（已否决）

- **官方开放平台互动 API（R24）**：B站/抖音等官方互动 API 对个人/自托管项目因企业
  资质门槛不可达，且覆盖面不满足十二平台统一底座需求。否决成立，但平台规则变化时
  应重新评估（长线最合规路线）。
- **ack/重投队列回执**：与 ws_server 广播语义（GAP 先例）冲突，解决的「AUTOlive
  离线时发送结果丢失」场景近乎不存在（发送请求本就来自 AUTOlive 在线连接）——
  尽力推送+审计日志权威对账替代。
- **多账号轮换发送**：规模化伪装基础设施（L 级新基建），与故障隔离的分账号评估是
  两个问题；未提案即未 defer，未来需要时重新提案。
- **维持 v1 约束（不实现发送）**：互动闭环永久缺「嘴」，上层产品价值锁死——与本次
  创始人裁定直接冲突。
