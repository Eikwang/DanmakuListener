# ADR-001: 引擎进程拓扑与抖音代理隔离

状态: ACCEPTED | 日期: 2026-09-27 | 关联: 阶段 0 工程前置 L（Eng 评审 A-1/A-2）

## 背景

六平台监听引擎的进程拓扑有三种可选：全同进程、全独立进程、按引擎风险分层。mitmproxy
代理内核持续解析不可信 TLS 流量，是全系统崩溃概率最高的组件；协议直连引擎是纯
asyncio WebSocket 客户端，故障域小。若代理与消息总线同进程，抖音侧一次崩溃或事件
循环阻塞将中断全部六平台的消息投递。

## 决策

1. **协议直连引擎（B站/斗鱼/虎牙/快手）：单进程单事件循环**，每平台每房间独立
   asyncio 任务；进程内带事件循环滞后 watchdog（loop lag 采样入 SYSTEM_STATUS/HEARTBEAT）。
2. **抖音代理引擎：默认独立进程**，经本机 IPC（WebSocket，复用统一消息契约线格式）
   接入消息总线；进程树预算单独核定并计入系统级预算统计边界。
3. 若实施中评估认为同进程集成收益显著，须先完成 **mitmproxy 嵌入宿主 asyncio 循环的
   技术 spike**（阶段 2 开工前），spike 失败即回退独立进程方案——该回退是 ADR 的
   强制部分，不是可选项。
4. 视频号受控后台引擎：宿主进程 + Playwright 浏览器进程树（Chromium 崩溃不扩散至宿主，
   Playwright 已隔离），每直播间独立 BrowserContext。

## 后果

- 抖音侧故障被隔离在代理进程内，常驻服务监护可单独重启它而不影响其他五平台。
- 多进程带来 IPC 序列化成本：统一消息线格式（contract schema.json）即 IPC 协议，
  无额外格式。
- 预算口径：协议引擎进程 ≤100MB、代理进程树单独核定、视频号进程树 ≤600MB、
  系统级（兜底关闭）≤1.2GB。

## 替代方案（已否决）

- 全同进程：故障隔离缺失（Eng A-1），否决。
- 全独立进程（每平台一进程）：进程数 ×6 常驻，运维与内存开销不成比例，否决。
