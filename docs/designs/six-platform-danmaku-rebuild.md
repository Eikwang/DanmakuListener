## Problem Statement

现有 DanmakuListener 以浏览器注入脚本为主监听路线，存在结构性内存泄漏：运行十几分钟内存占用高达几十 GB，当前靠定时重启浏览器硬扛——重启间隙弹幕丢失，电商客户投诉电脑卡顿。这不是代码质量问题，而是路线③（浏览器 DOM 注入）的结构性问题（页面 JS 堆累积、Chromium 多进程开销）。

重构目标：在现有 Python 包基础上，学习三个参考项目的监听逻辑，实现 B站、斗鱼、虎牙、抖音、快手、微信视频号六平台的无感监听（长时间稳定运行 + 低资源占用），并保留浏览器注入作为兜底能力。系统作为 AUTOlive（AI 直播数字人系统）的弹幕获取底座，AUTOlive 是唯一前端。

## Demand Evidence

- 电商公司客户与部分主播正在使用现有系统（Has users，未付费阶段）。
- 真实抱怨已到达：用户反馈「使用过程中电脑卡顿」，调查确认为内存泄漏——这是行为级证据（系统差到影响客户电脑正常使用），不是假设性需求。
- 客户多平台同时开播是硬约束：漏掉任何一个平台 = 客户的数字人在该平台瞎掉。这是六平台全量交付的商业依据（创始人面对楔子挑战时给出的证据）。
- 三个参考项目（DouyinBarrageGrab / barrage-fly / wxlivespy）的存在与活跃维护本身证明该需求有广泛受众。

## Status Quo

用户的四类土办法并存：

1. 用现有系统 + 定时重启硬扛：忍受内存暴涨与重启间隙的弹幕丢失。
2. 多个开源工具拼接：DouyinBarrageGrab、barrage-fly 等各管一两个平台，数据格式不统一，运维多个异构程序。
3. 人工盯屏 / 半手动：事后回放补数据。
4. 客户真正消费的是上层功能（AUTOlive 数字人互动、弹幕游戏），监听是无感知的底层环节——监听挂掉，上层功能全瞎。

真正的竞争对手是方案 1+2 的组合：客户已经忍受着它，说明痛点真实但尚未痛到全部迁移。重构的价值主张是把这个组合替换为单一稳定系统。

## Target User & Narrowest Wedge

- 目标用户：电商公司直播运营团队（AI 数字人带货直播间，多平台同时开播）+ 部分个人主播。直接集成方是 AUTOlive 系统（Python）。
- 最窄楔子：六平台无感监听全量交付。创始人明确拒绝「先抖音+快手」的分批楔子，依据是客户多平台同时开播的商业现实。架构按六平台一次性设计到位，工程上各平台独立完成、独立验证（完成一个即可接入 AUTOlive 内部验证），产品交付以六平台全量为准。

## Constraints

- Windows 为主要部署环境（客户机器），Python >= 3.10，与 AUTOlive（Python）集成。
- 无自有 UI：所有交互界面属于 AUTOlive。本系统的运维交互分两类（详见「运维与部署流程」）：部署时一次性人工步骤，以及运行期经统一消息通道向 AUTOlive 上报状态、由 AUTOlive 界面呈现的操作提示。
- 只监听、不发送弹幕/礼物。**（2026-10-06 修订：本条已由 ADR-002 部分解除——弹幕发送获准进入实施，礼物发送仍然禁止；发声主场景=仅自运营/受托直播间。见 docs/ops/adr-002-danmu-send-constraint-revision.md）**
- 部署形态必须纯净：电商客户机器上不能要求 Docker / Java 运行时 / 多个异构 exe。
- 性能约束（继承 specs/产品概述.md 并收紧）：弹幕延迟 < 1 秒；同时监听 10 个直播间（跨 >= 3 平台）时延迟与内存标准不劣化；内存预算见 Success Criteria 的量化表。
- 兼容现有 cookie/ 目录结构与既有配置体系。

## Premises（已确认，2026-09-27）

1. 核心价值是「长时间稳定运行 + 低资源占用」——客户抱怨的是卡顿（内存泄漏），不是功能不足。
2. 浏览器注入从主路线降级为兜底路线（保留可用性，不再投入主力量优化它的内存问题）。
3. 技术栈保持 Python（现有包 + AUTOlive 集成约束），学习参考项目的协议逻辑用 Python 重新实现，不移植 C#/Java/TS 代码。
4. 按平台选引擎而非统一引擎：抖音→代理/伴侣直听；B站/斗鱼/虎牙/快手→协议直连；视频号→官方管理后台借用。
5. 产品形态是「监听引擎层 + 统一消息推送」，无自有 UI，AUTOlive 是唯一前端。

## Approaches Considered

### Approach A: 侧车集成外部工具（拒绝）

把 DouyinBarrageGrab.exe、barrage-fly（Java/Docker）、wxlivespy.exe 作为侧车进程，Python 只做统一接入归一化。工作量 S/M、协议维护外包上游。**拒绝原因**：部署重（客户机器需 Java + 多个异构 exe），与「AUTOlive 的 Python 包」定位冲突，且受上游项目停更/变动的牵制。

### Approach B: 全自研协议直连（拒绝）

六平台全部 Python 协议直连，无浏览器无外部进程。控制力最强。**拒绝原因**：微信视频号没有公开协议直连路径，强行逆向是高风险长周期工程；同时放弃 barrage-fly 已验证的协议栈资产去重造轮子。实际不可达六平台目标。

### Approach C: 混合分层引擎（选定）

按平台特性分配引擎路线，Python 自研为主，每条路线都有参考项目可对照：

| 平台 | 引擎路线 | 参考实现 |
|------|---------|---------|
| B站 | 协议直连（WebSocket） | barrage-fly / ordinaryroad-live-chat-client |
| 斗鱼 | 协议直连 | 同上 |
| 虎牙 | 协议直连 | 同上 |
| 快手 | 协议直连 | 协议对照源：barrage-fly 所依赖协议库中的快手实现（ordinaryroad-live-chat-client 的 kuaishou 模块，**须单独获取，不随 barrage-fly 仓库内嵌**，见 Dependencies）；本项目 `直播监听脚本/` 目录已有本地逆向工件可交叉验证：`ks.proto`、`ks_pb2.py`、`kuaishou_pb2.py`、`快手逆向.js` |
| 抖音 | 代理/直播伴侣直听 | DouyinBarrageGrab（现有 proxy_engine 扩展，`直播监听脚本/dy.proto` 已有） |
| 微信视频号 | 受控后台借用 | wxlivespy（官方直播管理后台单页面 + 网络层拦截，非 DOM 注入） |
| 全平台兜底 | 浏览器注入 | 现有 browser_engine 保留（验收与触发语义见下文） |

## Recommended Approach

**方案 C：混合分层引擎。** 它是五条前提的逻辑必然（Python 技术栈 + 按平台选引擎），每条路线都有已验证的参考实现对照，部署形态保持单一 Python 系统满足电商客户机器的纯净要求。

### 引擎路线与多直播间复用方式

1. **协议直连引擎**（B站/斗鱼/虎牙/快手）：Python WebSocket 协议客户端。**每个直播间一条独立长连接**（asyncio 任务级隔离，单房间故障不影响其他房间）。消息抽象对照 barrage-fly 的统一消息设计（见下文消息契约）。
2. **代理/伴侣直听引擎**（抖音）：扩展现有 `proxy_engine`，学习 DouyinBarrageGrab 的进程过滤 + 域名白名单 + protobuf 解析。**进程级共享**：一个代理服务实例承载多个浏览器/伴侣来源的多房间流量，无需每房间建实例。
3. **受控后台引擎**（视频号）：受控浏览器打开官方直播管理后台，网络层拦截抓取（wxlivespy 验证的路线）。**每个直播间一个独立 BrowserContext 页面实例**（继承现有 Playwright 隔离模式），页面崩溃不扩散。多房间并行时登录态经 storageState 导出后注入各 BrowserContext；**「同一微信账号多 BrowserContext 并行监听多直播间」是否触发微信多端互踢/登录风控尚未验证**，列为部署前验证项（见 Open Questions），若触发风控则降级为「每直播间独立微信账号」方案（部署与运维影响同步升级）。
4. **浏览器注入兜底引擎**：现有 `browser_engine` 降级保留。触发语义见下文「兜底引擎边界」。
5. **统一消息总线**：沿用现有 `bus/`（标准化格式、滑动窗口去重、事件分发），输出对接 AUTOlive。

### 统一消息契约（九类）

八类业务消息对照 barrage-fly 的统一协议原文（DANMU、GIFT、SUPER_CHAT、ENTER_ROOM、LIKE、LIVE_STATUS_CHANGE、ROOM_STATS、SOCIAL），另加一类本系统扩展的系统状态消息：

1. DANMU（弹幕）
2. GIFT（礼物）
3. SUPER_CHAT（醒目留言）
4. ENTER_ROOM（进房）
5. LIKE（点赞）
6. LIVE_STATUS_CHANGE（直播状态变更）
7. ROOM_STATS（房间统计）
8. SOCIAL（社交行为：关注/粉丝团）
9. **SYSTEM_STATUS（系统状态，本系统扩展）**：引擎存活心跳（引擎→AUTOlive，默认每 10 秒一条，AUTOlive 侧连续 3 个周期未收到判定引擎失联并告警——与引擎对平台连接的静默检测是两个独立机制，两者参数均纳入契约 v1 Schema）、房间在线状态、断线缺口（GAP）标记、登录态需求（NEEDS_LOGIN）、当前活跃引擎标识、背压丢弃计数、平台路线失效/降级告警。此清单为契约 v1 的起点，**最终以契约 v1 Schema 为权威载荷目录**。

SYSTEM_STATUS 为必选行为而非可选增强：协议静默掉线、页面崩溃、登录态过期时，AUTOlive 必须能从消息通道得知（解决「引擎无声挂掉、上层持续瞎跑」）。断线重连后的缺口处理策略：不承诺回补，但**必须**发出 GAP 标记消息（含平台、房间、缺口时间窗），使上层对数据连续性有明确认知。

### 兜底引擎边界

- **服务场景**（明确列举）：① 不在六平台范围内的长尾平台临时需求；② 某平台协议直连/代理路线因平台风控升级临时失效、新协议适配未完成期间；③ 客户环境禁用代理与 hook 模式（网络策略/杀软）时的降级。
- **激活方式**：v1 定义为**配置文件人工开关**（按平台指定启用兜底），不做自动故障切换；自动切换列为 v2 候选。
- **决策者**：运维/配置决定启用与切回；当前活跃引擎标识随 SYSTEM_STATUS 消息上报，AUTOlive 界面可见。
- **验收**：兜底引擎与主路线引擎适用同等内存预算；**有界会话**——单页面生命周期上限 4 小时，到期后事件驱动重建（替代全局定时重启），重建前后各发一条 SYSTEM_STATUS；重建窗口的 GAP 语义与断线一致。
- **「基本内存治理」范围**：有界会话重建、独立 BrowserContext 隔离、页面堆大小监控（超阈值提前触发重建并上报）。

### 运维与部署流程（与「无自有 UI」的衔接）

| 事项 | 时机 | 执行方式 |
|------|------|---------|
| 抖音代理模式：TLS 证书信任、端口确认 | 部署时一次性 | 人工管理员步骤（安装自签名证书到系统信任存储；默认端口 8827 冲突时可配置） |
| 抖音 hook 模式：直播伴侣安装/路径配置/index.js 还原 | 部署时一次性 + 伴侣升级后 | 人工部署步骤（含还原 `index.js.bak` 的操作说明） |
| 视频号：微信扫码登录 | 部署时一次性 | 人工扫码；登录态持久化到 cookie/ 目录 |
| 视频号：登录态过期（7x24 运行期间） | 运行期 | 引擎发出 NEEDS_LOGIN（SYSTEM_STATUS），AUTOlive 界面提示操作人重新扫码，扫码后引擎自动恢复 |
| 兜底引擎开关、代理/hook 子路线选择 | 配置变更时 | 配置文件人工修改 |

### 抖音子路线选择准则

- **代理模式（默认）**：覆盖浏览器、抖音客户端、直播伴侣全部来源；前提是客户机允许安装受信证书、代理端口可用、可修改系统代理（或按来源浏览器显式指定代理）。
- **hook 模式（备选）**：免系统代理，仅覆盖直播伴侣来源；用于代理模式不可用的环境（网络策略禁止、杀软拦截证书安装）。
- 部署前按客户环境清单（杀软、防火墙、直播伴侣版本、端口占用）选择子路线，列入部署兼容性验证。

## Open Questions

- 视频号官方管理后台页面/接口结构的稳定性：微信更新可能改变后台，需要版本检测与失效告警（失效时经 SYSTEM_STATUS 上报）。
- 视频号「同一微信账号多 BrowserContext 并行监听多直播间」的风控验证（部署前实测）：是否触发多端互踢或登录风控；若触发，评估「每直播间独立微信账号」方案的部署前提与运维影响。
- ordinaryroad-live-chat-client 的本地获取与版本锚定方式（见 Dependencies）。
- 现有系统重构后 DouyinBarrageGrab「有一些问题，现在先不处理」的具体清单——学习时需明确避免继承的缺陷集合。
- 电商客户环境样本（杀软、防火墙、直播伴侣版本分布）用于部署兼容性验证。

## Success Criteria

- **容量标准**：同时监听 10 个直播间（跨 >= 3 平台）时，延迟与内存标准不劣化。
- **延迟**：六平台弹幕延迟均 < 1 秒。
- **内存预算（可度量）**：
  - 计量对象与合成规则：协议直连引擎以「引擎进程」计量（多房间共享单 asyncio 进程，预算不随房间数扩展）；受控后台引擎与兜底引擎以「浏览器进程树总 RSS」计量（Chromium 共享的主进程/GPU/网络进程计入进程树，不做单页面归属拆分）；系统级预算 = 全部引擎进程树 RSS 之和。
  - 预算值：协议直连引擎进程 ≤ 100 MB（多房间总量）；受控后台引擎进程树 ≤ 600 MB（满配多房间）；兜底引擎进程树 ≤ 400 MB；系统级总预算 ≤ 1.2 GB（10 直播间跨 ≥ 3 平台满配压测时）——对比现状的十几分钟几十 GB。
  - 漂移：每进程树 24 小时增量 ≤ 10%（即基本无增长趋势）。
  - 测量方式：psutil 按分钟采样进程树 RSS 曲线；观察窗口：24 小时标准压测 + 7 天试点直播间实测。
- **连续性**：断线自动重连；重连后 GAP 标记消息必达 AUTOlive；平台连接静默检测超时（可配置，默认 30 秒）触发重连与状态上报；引擎存活心跳默认 10 秒/条，AUTOlive 侧连续 3 个周期（30 秒）未收到判定引擎失联（两套心跳参数均以契约 v1 Schema 为准）。
- **重启机制**：移除「全局定时重启浏览器」手段，替换为事件驱动的有界会话重建（兜底引擎与受控后台引擎适用），重建对上层可见（SYSTEM_STATUS）。
- **契约完整**：九类消息 × 六平台的统一格式落地，AUTOlive 无需按平台区分处理；SYSTEM_STATUS 覆盖六平台与兜底引擎。
- **交付节奏**：每平台完成即接入 AUTOlive 内部验证通过；产品交付为六平台全量。

## Distribution Plan

- 交付形态：AUTOlive 内嵌组件 + 独立 Python 包（`pip install` / 随 AUTOlive 打包分发到客户机器）。
- 无独立分发渠道与 CI/CD：当前为本地仓库（无远程），随 AUTOlive 的部署流程走。建立远程仓库与 CI 属于后续工程化依赖项，不阻塞本次重构。

## Dependencies

- **AUTOlive 侧的消息消费契约确认**（接口设计输入，见 The Assignment）。
- **三个参考项目本地可用**：DouyinBarrageGrab（C#，`DouyinBarrageGrab/`）、barrage-fly（Java，`ordinaryroad-barrage-fly/`）、wxlivespy（TS/Electron，`wxlivespy/`）。
- **ordinaryroad-live-chat-client**（barrage-fly 的协议实现核心库）：四条协议直连路线的真正对照源。版本锚定：以本地 barrage-fly 仓库依赖声明所引用的版本为准；该库未随 barrage-fly 仓库内嵌，需单独获取源码（Maven Central 或 GitHub），获取方式在实现前确认。
- **本地 proto 工件**：`直播监听脚本/` 目录（dy.proto、ks.proto 及生成文件）作为抖音/快手协议的交叉验证基础。
- DouyinBarrageGrab 已知问题清单（用户提到「重构后有一些问题，现在先不处理」，需要明确清单避免继承）。
- 电商客户环境样本（杀软、防火墙、直播伴侣版本分布、代理端口占用）用于部署兼容性验证。

## The Assignment

**写出 AUTOlive ↔ DanmakuListener 的统一消息契约 v1**，范围包括：

1. **消息 Schema**：九类消息 × 六平台的字段对照表（JSON Schema，含必选/可选/平台特有字段）；
2. **传输与投递语义**：输出通道形式（默认本机 WebSocket 推送，可选 HTTP 回调）、单房间内消息顺序保证、投递级别（at-least-once + 去重窗口，允许重复但去重后不重）、AUTOlive 消费过慢时的背压策略（有界环形缓冲 + 丢弃计数经 SYSTEM_STATUS 上报）、消息总线自身的重连行为。

然后拿给一个真实电商客户，对照他们的实际使用场景（数字人何时需要什么消息）过一遍。

### R3-1 — completeness

**Problem**

> 7x24 无人值守运行下「直播结束→再开播」的引擎行为未定义：主播下播后平台会关闭或静默弹幕连接，将触发已承诺的静默检测（默认 30 秒）与断线自动重连，但文档未定义对不在线房间的重试策略（重试间隔/退避/是否无限循环）、下播期间 SYSTEM_STATUS 房间在线状态如何流转、再开播后是否自动恢复监听。鉴于文档自认「漏掉任何一个平台 = 客户的数字人在该平台瞎掉」，再开播自动恢复是必需行为，当前口径下实现者无法判定重连循环语义与恢复责任。

**Remedy**

> 在 Success Criteria 连续性条或引擎路线节补充「房间在线/离线生命周期」行为：下播时上报房间在线状态=离线、对离线房间采用有界退避重连（如指数退避加上限）、再开播时自动重新订阅并上报恢复，并说明下播期间与 GAP 语义的边界（下播期间不产生缺口标记）。

### R3-2 — completeness

**Problem**

> 内存预算口径未覆盖全部引擎组件：引擎路线清单共五个组件（协议直连、代理/伴侣直听、受控后台、浏览器注入兜底、统一消息总线），而 Success Criteria 只定义了协议直连（≤ 100 MB）、受控后台（≤ 600 MB）、兜底（≤ 400 MB）三类预算；抖音代理/伴侣直听引擎按文档自身术语（前提 4：抖音→代理/伴侣直听，区别于协议直连）不属于「协议直连」，其计量对象与预算值缺失；统一消息总线是否为独立进程、是否计入「全部引擎进程树 RSS 之和」亦未说明。这影响系统级 ≤ 1.2 GB 总预算求和范围的封闭性与逐引擎验收的可判定性。

**Remedy**

> 为抖音代理/伴侣直听引擎补充计量对象与预算值（或明示并入协议直连引擎的进程预算口径）；明确统一消息总线的进程归属（与引擎同进程或独立进程）及其是否计入系统级总预算，使系统级求和范围封闭。

### R3-3 — clarity

**Problem**

> 有界会话 4 小时上限对受控后台引擎的适用性只能推断：该数值仅出现在兜底引擎边界的验收条（「单页面生命周期上限 4 小时」），其中「兜底引擎与主路线引擎适用同等内存预算」的「同等」在文法上只修饰内存预算；Success Criteria 重启机制条写「有界会话重建（兜底引擎与受控后台引擎适用）」但未给出受控后台页面的生命周期数值。视频号页面是否每 4 小时重建涉及 GAP 与再扫码风险窗口，实现者需要明确数值而非推断。

**Remedy**

> 在受控后台引擎条目或 Success Criteria 重启机制条明示受控后台页面适用同一 4 小时生命周期上限（或给出其独立数值），并确认其重建窗口同样发 SYSTEM_STATUS 与 GAP 标记。

### R3-4 — clarity

**Problem**

> 「六平台弹幕延迟均 < 1 秒」缺少可判定的测量口径：延迟的起止点（平台侧发出时间、本系统收到时间、还是送达 AUTOlive 时间）与参考时钟来源未定义，各平台消息自带时间戳的可用性、精度与时钟偏差处理未提及；容量标准「延迟…不劣化」也因此缺基线。对比之下内存预算已给出 psutil 按分钟采样与观察窗口的测量方式，延迟准则在验收时无法裁决。

**Remedy**
