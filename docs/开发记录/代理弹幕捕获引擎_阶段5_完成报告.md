## 完成任务

### Task-13: WebSocket 断线重连

**实现文件**：
- `danmaku_listener/engines/danmaku_addon.py`（`websocket_end` 方法填充）
- `danmaku_listener/engines/proxy_engine.py`（`_on_addon_message` 增加 ws_disconnect 处理）

**核心逻辑**：

1. **DanmakuAddon.websocket_end()**：
   - 检查 `flow.id` 是否在 `_active_ws_flows` 中（已注册的弹幕流）
   - 如果是，`pop` 移除该 flow，获取 `room_id`
   - 通过 `asyncio.create_task` 调用 `_message_callback({type: "ws_disconnect", room_id})`
   - 不在 `_active_ws_flows` 中的 flow 直接忽略（非弹幕流或未注册的连接）

2. **ProxyEngine._on_addon_message()**：
   - 新增 `ws_disconnect` 消息类型处理分支
   - 收到 `ws_disconnect` → 构造 `ConnectionError` → 调用 `_handle_error_with_reconnect(room_id, error)`
   - `_handle_error_with_reconnect` 继承自 `BaseEngine`，集成 `ReconnectManager` 指数退避重连
   - 重连成功 → `_emit_message({type: "reconnect_success", room_id})`
   - 重连失败 → `_emit_error(ConnectionError(...))`
   - 无 ReconnectManager → 直接 `_emit_error`

**关键设计决策**：
- 代理模式下的"重连"不是主动重建 WebSocket（由浏览器自动完成），而是检测断开后等待浏览器重新建立 WS 连接
- `websocket_end` 通过 `_active_ws_flows` 判断是否为弹幕流，而非重新匹配域名——因为 flow 在 `websocket_start` 时已注册，断开时只需查表
- `room_id` 从 `_active_ws_flows` 缓存中获取，确保断线和重连使用同一 room_id

## 技术决策记录

1. **websocket_end 使用 _active_ws_flows 判断**：不重新匹配域名，而是通过 `flow.id in _active_ws_flows` 判断。这确保只有 `websocket_start` 已识别的弹幕流才会触发断线事件，避免误触发
2. **ProxyEngine 消息路由**：`_on_addon_message` 新增 `ws_disconnect` 分支，将断线事件路由到 `_handle_error_with_reconnect`，复用 BaseEngine 已有的重连基础设施
3. **异步测试模式**：`websocket_end` 内部使用 `asyncio.create_task`，测试需用 `@pytest.mark.asyncio` + `async def` 确保事件循环存在
